# 玩家发布日志写法

你正在动玩家发布日志。先确认：**用户是否说了开发完成、要发新版本？**
如果没有，停手——开发期一律不动这两个文件，开发中的改动记进
`GreyWardenPolicePurity/docs/state/`。

理由：在研功能会反复改形状、也可能整个回滚，玩家日志描述的是**交付出去的形态**，
不是走到那里的路线。

## 内容

- **玩家的基础是上一个正式发布版的游戏内容**（用户裁定 2026-09-25）。每条都写"和上一版相比
  玩家看到什么变了"。开发期间引入又修掉的问题、中途推翻的方案、测试过程，玩家从没见过，不写；
  只有上一版就存在的问题被修掉时才进"修复"。
- **不泄露内部机制**（用户裁定 2026-09-25）：不写机制名、诊断/监控、欲望、打分、门禁、补丁、
  AI 代理、开发流程之类的字样。先例：r12 的协力军团提示文字因此被删。
- 保持简洁，可以直接当公开发布贴复用。它只回答三件事：什么时候加了玩家可见的改动、
  改了什么、现在有什么内容可玩。
- 每个有意义的玩家可见功能或结果用一条短 bullet。条目数量要够区分实质不同的改动，
  **不要为了简短把整次更新压成一句含糊的话**。相关的小调整可以合并。
- **省略**：触发次数、精确数值增益、上限、公式、实现细节、无关紧要的调整说明。
  这些记进 `docs/state/`。
- 按功能总结现有可玩系统，不是写完整手册。让玩家在游戏里发现次要行为；
  不要塞进内部推理、穷举公式、长 FAQ、测试历史或每个边缘情况。
- 从玩家视角写。只有在省略会实质妨碍玩家做必要决策时才写出精确数值。
- 避免只对实现有意义的措辞（回调、补丁、合成打击、资产管线步骤、私有引擎字段），
  除非玩家必须靠它理解结果。

## 组织

- 每个发布按日期/版本归档，下设简短的 `新增与调整` 和 `修复` 列表。
- **不要加 `未改动` 段落。** 只有在省略某个未变行为会让已改机制产生实质误导时才提它。
- 两份 README 各保留**恰好最近两个**正式发布条目，最新在前。例如 `r5` 包内含 `r5`
  和 `r4`；发 `r6` 时保留 `r6` 和 `r5`、删掉 `r4`。每条说明它与紧邻的前一个发布相比。
- 一个待发布版本的多次开发迭代**合并进该版本的单一条目**，不要加独立的开发日志。

## 发布后

- 构建/部署后，核对复制进 live 模块的 README 与仓库版本一致。
- release 正文由这两份 README 的对应段落**程序化抽取**，不手写，避免漂移。
