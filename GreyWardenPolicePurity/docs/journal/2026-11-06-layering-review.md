# 分层与测试方向调研

## 问题与判断

用户希望判断分层、清洁度与优雅程度优化是否走在正确方向，并参考成熟模组的开发与测试经验，减少依赖玩家发现难复现故障的循环。本次为调查，没有新业务裁定。当前实现与未结事项只见 state/code-health.md 和 workflow.md 清理待办。

判断：分开游戏状态采集、业务决定和游戏动作执行，能够降低判断错误的复现成本；但真实游戏对象如何失效、回调先后和动作副作用，仍需游戏内验证。单次输入快照的回放不能重现整段事件时序，旧决定也只能作为重构等价性依据，不能自动充当正确玩法的标准。

## 外部证据（2026-11-06 查阅）

- [Bannerlord Coop 仓库指南](https://github.com/Bannerlord-Coop-Team/BannerlordCoop/blob/development/AGENTS.md)：公开说明游戏入口、核心逻辑、游戏接口和各类测试的职责；CI 同时跑单元测试与 E2E 分片。可借鉴职责边界和多层验证，不从目录结构推断其游戏行为已经完备验证，也没有复制其实现。
- [ButterLib 测试工作流](https://github.com/BUTR/Bannerlord.ButterLib/blob/dev/.github/workflows/test.yml)：获取 stable/beta 游戏依赖，在多个构建配置执行测试并生成覆盖率报告。适合借鉴实际游戏版本兼容检查；该 YAML 本身不能证明完整战役流程已自动化。
- [NeoForge Game Tests](https://docs.neoforged.net/docs/misc/gametest/)：游戏内场景由模板、环境、测试函数与测试实例组合，设置准备时间、运行期限及通过条件。对本项目最有用的是可重复建立前提、限定等待、检查真实结果；不依赖世界恰好存在可用目标。
- [Factorio FFF #54](https://www.factorio.com/blog/post/fff-54)：开发团队介绍创建实体后保存、加载并核对状态保真的测试，以及关键点校验值。这是游戏本体经验，不是某个模组的交付证据；可借鉴存读档前后的业务状态比较。
- [Factorio FFF #288](https://factorio.com/blog/post/fff-288)：列举由自动崩溃日志发现的时序组合故障，并说明一些很小的修复需要数小时到一天寻找复现步骤。难复现并不直接说明架构差，证据采集与复现工具仍是独立投入。

## 建议的试点收尾顺序（agent 建议，未作为新规则）

1. 先让测试桥能稳定搭出一宗有效住城案件和实际派队条件，区分“前提没建立”和“业务失败”。造前提经原版动作与本模组既有入口，不直接写出预期补派/结案结果。
2. 在真实游戏里走通派出、失队、补派、抵达、结案、返还，并在失队待补派等中间状态插入存读档。查询事件和状态，在期限内等待条件成立，避免只固定快进一天。
3. 录下进入决定前的输入、新旧决定和动作后的实际结果；回放样本非空且覆盖目标分支，缺样本明确报告未验证。根因修复场景仍按既有流程保留旧错新对的负对照。
4. 在迁移等价性之外，用独立业务要求判断正确性，例如结算只发生一次、兵员转移可核对、失队不会抹掉尚未完成的指派。组合事件先后进行探索，并保存失败序列；不要让旧实现的错误变成永久期望值。
5. 试点闭合后才切换生产执行并删除旧分支及影子脚手架，再迁移下一子系统。全过程以一个业务变化涉及多少职责、失败能否定位和复现衡量收益，不用类数、文件长度或测试总数替代。

纯业务规则测试直接执行生产的同一份逻辑，与另写假游戏验证自身假设有本质差别；建议后续明确两者的验证范围。现行文字与试点实现的口径差异已登记，本轮未改写用户此前的测试限制。
