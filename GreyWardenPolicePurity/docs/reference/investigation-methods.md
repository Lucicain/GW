# 调查方法与证据强度

原版行为不明时，**先查证，再改代码**。不要靠猜测反复实测去"试出"机制，也不要让
用户实测来回答本该从原版代码里查到的问题。2026-09-24 的弓↔双刀切换在几十轮
猜测式修改后没有解决，反汇编原生引擎一次查实根因，改完一次通过。

本文件记录**怎么查**。查出来的结论写进对应的 `docs/state/*.md`，并标上依据（见文末）。

## 证据强度，从强到弱

| 等级 | 方法 | 能回答什么 | 典型陷阱 |
|---|---|---|---|
| `C++反汇编` | 反汇编 `TaleWorlds.Native.dll` | 引擎（C++）里的真实规则：AI 选武器、命中、物理、动作 | 地址只对当前游戏版本有效；换版本要重查 |
| `C#反编译` | ilspycmd 反编译托管 DLL | 托管层的逻辑、调用链、谁调了谁 | 看不到 C++ 里发生的事；只读到"托管层把请求交出去了"不等于引擎照做 |
| `运行时反射` | 直接加载游戏 DLL、调私有方法 | 某个托管方法在给定输入下实际返回什么 | 脱离游戏运行环境，引擎状态是假的 |
| `崩溃转储` | cdb 读 WER 转储 | 崩在哪个原生函数、寄存器和调用栈 | 转储常缺堆页，指针指向的对象可能读不到 |
| `实机诊断` | `GWP_DIAGNOSTICS` 日志 | 实际发生了什么、多频繁 | **可能被 bug 污染**：`_applied` 静态开关曾让设置只在进程第一局生效，前后观察因此互相矛盾 |
| `实机观察` | 用户或测试者在游戏里看到的 | 结果对不对、手感好不好 | 看得到现象，看不到原因 |

另有一类依据不是调查方法：`用户裁定`（用户决定要这样）和 `设计`（我们选的方案）。
它们**不会被更强的调查方法推翻**，只能由用户改。

## C++ 反汇编（`TaleWorlds.Native.dll`）

依赖：`pip install pefile capstone`（本机已装：pefile 2024.8.26、capstone 5.0.7）。

游戏目录：`D:\steam\steamapps\common\Mount & Blade II Bannerlord\bin\Win64_Shipping_Client\`

**按函数反汇编，不要从 `.text` 开头线性扫。** `.text` 里夹着跳转表和填充字节，
capstone 遇到第一个无法解码的字节就停，线性扫只覆盖开头一小段，还不报错。

- 函数边界来自 `.pdata`（`pe.DIRECTORY_ENTRY_EXCEPTION`，每项有 `BeginAddress`/`EndAddress`）。
- 叶函数没有 `.pdata` 项，从调用处拿到地址后直接从该地址反汇编。

**从托管调用找到 C++ 函数：** 托管层的 `MBAPI.IMBxxx` 调用按编号交给引擎。

1. 编号在 `TaleWorlds.MountAndBlade.AutoGenerated.dll` 的 `CoreInterfaceGeneratedEnum` 里
   （用 ilspycmd 反编译这个 DLL 就能看到）。
2. 引擎在 `EngineApiMethodInterfaceInitializer` 里按编号注册函数，指令序列形如
   `lea rdx,[rip+fn]; mov ecx,<编号>; call [rbx+0x108]`。在这段里按编号找到 `lea` 的目标，
   就是该接口的 C++ 实现。
3. 2026-09-24 用这个方法对上了 602 个接口地址，其中包括 `invalidate_ai_weapon_selections`。

**引擎层接口（`TaleWorlds.Engine` 的 `Scene` 等）编号不在上面那个枚举里：**

1. 编号是 `TaleWorlds.Engine.AutoGenerated.dll` 里 `ManagedCallbacks.ScriptingInterfaceObjects` 的私有嵌套枚举
   `EngineInterfaceGeneratedEnum`（从 0 顺序编号，按声明次序数）；`SetFunctionPointer` 的 switch 把编号对到
   `ScriptingInterfaceOfIXxx.call_XxxDelegate`。
2. 引擎注册的指令序列是 `lea r8,[rip+fn]; mov edx,<编号>; mov rcx,rbx; call <注册函数>`。
3. 例：`enm_IMono_Scene_get_path_distance_between_ai_faces` = 944（0x3B0），注册在 `0x180395826`，实现在
   `TaleWorlds.Native+0x4D6340`（游戏版本 v1.4.8，换版本要重查）。（依据：C++反汇编 2026-10-16）

**从字符串找到 C++ 函数：**

```bash
python tools/native/find-string-refs.py "<游戏目录>/TaleWorlds.Native.dll" "某条日志或断言文字"
```

它找出所有 `lea reg,[rip+…]` 指向该字符串的指令，并打印附近的反汇编。
约 6800 个字符串里有约 4300 个能这样直接找到；其余是通过指针表引用的，
**引用数为 0 不代表原版没用它**。

> 2026-09-25 修正：这个脚本原在 `.codex_tmp/analyze_native_refs.py`，用线性扫描，
> 对 `Invalid reference frame` 报 0 处引用，实际有 2 处。凡是依据旧脚本
> "0 处引用"得出的结论都不可信。

**记录：** 查实的地址、偏移、判断条件写进对应 state 文件（例：`dual-blade.md` 的
「原版 AI 换武器机制」一节），注明游戏版本。换游戏版本时这些地址要重查。

## C# 反编译（托管 DLL）

工具：`ilspycmd`（9.1，在 `~/.dotnet/tools/ilspycmd`）。

```bash
ilspycmd -p -o <输出目录> "<游戏目录>/TaleWorlds.MountAndBlade.dll"
```

- 已有的反编译输出在 `.codex_tmp/` 下，例如 `mb148-decomp/`、`core148-decomp/`、
  `campaignsystem-full-decompile/`。这个目录被 git 忽略，**随时可以重新生成**，
  不要把它当成唯一副本来引用。
- 也用来检查**我们自己构建的 DLL**：例如确认玩家包里诊断代码确实被编译掉了。
- 托管层读到的"请求"不等于引擎的"结果"。弓↔双刀切换在托管层看起来完全正常，
  真正的决定在 C++ 里。

## 运行时反射

直接 `Assembly.LoadFrom` 游戏 DLL，用 `FormatterServices.GetUninitializedObject`
造出对象，只设置需要的字段，再调用私有方法看返回值。先例：
`.codex_tmp/check-native-persuasion-direct.ps1`（说服成功率计分）。
适合回答"这个纯函数在这些输入下算出什么"，不适合依赖引擎状态的逻辑。

## 崩溃转储

- WER 转储在 `%LOCALAPPDATA%\CrashDumps\TaleWorlds.MountAndBlade.Launcher.exe.<pid>.dmp`。
- 用 Windows SDK 的 cdb：`cdb -y . -z <dmp> -c ".ecxr; kb; q"`。
  本机的 cdb 来自 WinDbg 商店版：`%LOCALAPPDATA%\Microsoft\WindowsApps\cdbX64.exe`（2026-09-27 确认可用）。
- 托管崩溃再加 SOS：`.loadby sos clr; !pe -nested; !clrstack` 读出异常类型和托管栈。Harmony 改写后的方法是动态方法，
  SOS 显示为 `<unknown>`、`!ip2md` 认不出，JIT 代码页和托管堆通常也不在 WER 转储里（`!dso` 报读不到堆段）；
  这时只能确认调用链，具体哪个引用为空要靠首次异常记录的 IL 偏移或针对性诊断。（依据：实机转储 2026-10-22）
- 转储常缺堆页：能看到崩在哪个函数和寄存器，但指针指向的对象可能读不出来，
  不要因此把它"精确指认"到某个士兵或物体。
- 游戏无提示关闭、没有转储也没有系统记录时，先查 Steam 的退出码：`<Steam>\logs\console_log*.txt` 里
  「no longer tracking PID <pid>, exit code …」。`-2147023895`（0x800703E9，COR_E_STACKOVERFLOW）是 .NET 栈溢出：
  进程立即结束，模组的首次异常观察、TaleWorlds 看门狗和 WER 都拿不到东西；`-1073741819`（0xC0000005）是原生访问违例。
  游戏进程的 PID 见 `watchdog_log_<pid>.txt` 的文件名。（依据：实机诊断 2026-10-16）
- 抓无提示闪退现场：用户运行 `tools/Capture-StackOverflow.ps1`（可加 `-ContinueGame`），它在 cdb 下按启动器同样的模块参数启动游戏，
  整个调试会话写进 `Documents\Mount and Blade II Bannerlord\GreyWarden-Crash-<时间>.log`。常规首次异常放行；栈溢出（sov），以及访问违例、
  CLR 异常、fail-fast（c0000409）的第二次机会（即致命的那一次）时，先保存`.exr -1`/`.ecxr`寄存器、`kv`带地址的原生栈和同名`/mip`转储，再读SOS `!pe` / `!clrstack -a`与全部线程栈。
  `/mi`增加栈间接引用的内存，`/mp`增加PEB/TEB，不等于全堆转储，解释见[Microsoft文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/user-mode-dump-files)。
  CLR直接带栈溢出状态终止时，在`ntdll!RtlExitUserProcess`的ecx和`NtTerminateProcess`的edx为0x800703E9或0xC00000FD时提前留现场；此入口无异常上下文，不用`.ecxr`。其余退出原样继续。
  调试器默认MASM表达式的逻辑并用`or`，不能写C#的`||`；两种故障码和正常0码条件已在现有转储离线求值通过，真实进程断点尚待验证。
  收集完关掉游戏；游戏自己退出时记下退出码。在调试器下 Windows 不写 WER 记录，Steam 也不记退出码，
  所以只有这份日志。cdb 引号命令串里反斜杠是转义符，路径要写成双反斜杠。agent 不运行它。
  （依据：实机诊断 2026-10-16：第一版只处理栈溢出，22:28 那次闪退什么也没留下）
- 先核对RGL是否已经进入退出清理，再将转储归类。`Managed Interface deleted`之后的释放错误不能作为大地图业务闪退证据；最后一条业务日志也不证明下一步已经执行。没有首次托管异常记录不能排除栈溢出。先用被动前后边界分段，再由转储指认具体调用。（依据：用户确认、23:10退出转储与原版Army调用链复核2026-10-16）

## 实机诊断

见 `docs/state/diagnostics.md`。要点：诊断日志是**现象**的证据，不是**机制**的证据。
读日志前先确认产生日志的代码本身没有 bug，并确认测试时 live 模块与仓库一致。

## 依据标注

`docs/state/*.md` 里对以后开发起约束作用的硬规则（"不要 X""不得 Y""不要恢复 Z"），
在句末标注依据：

```
- 不要放行双刀在手时的单独收副手……（依据：C++反汇编 2026-09-24；实机 2026-09）
```

可用的依据：`用户裁定` `设计` `流程` `C++反汇编` `C#反编译` `运行时反射` `崩溃转储` `实机诊断` `实机观察`。
`流程` 用于开发流程本身的约定（不手改生成文件、部署后比对哈希等）。

**有了更强的方法时**：`grep -n '依据：' docs/state/*.md`，找出依据比新方法弱、
又正好是新方法能回答的规则，逐条复查。复查后更新依据；被推翻的规则原地改写，
旧的想法留在 journal 里。

`tools/Check-StateFreshness.py` 会列出没有标依据的硬规则。


## 离线测试与完整战役模拟的证据边界

用户要求按特定场景完整推进双方原版AI、当前模组、移动、进出城及后续战斗，不用只执行局部方法的通过数替代，也不预设目标必然离城或追截队会消失。（依据：用户澄清 2026-10-19）

- 方法回归：实际生产/新反编译方法执行，其他业务或引擎状态作为输入；只能证明对应方法的决策。
- 托管联动：双方原版评分、完整移动解算、原版离城谓词等直接相接；若导航到达、最终动作提交或战斗结果仍是夹具，明确指出边界。没有手设目标出城也不等于完整原生战役。
- 完整战役：真实原生地图/导航、时间循环、全部原版行为与本轮模组共同运行；报告实际宿主、版本、模组及存档/新世界。隐藏窗口不等于无图形引擎；没有运行这些不能称“后台跑了骑砍”。

当前仓库只具备前两级，尚无经验证的完整无界面战役宿主。本机bin仅发现Client/Editor布局，CampaignGameMode只有None/Campaign/Tutorial；这不证明第三方或自行开发宿主不可能。官方Dedicated Server文档描述多人Mission，不直接提供单人战役测试入口。社区[BUTR Bannerlord.GABS](https://github.com/BUTR/Bannerlord.GABS/blob/master/docs/setup-guide.md)通过MCP控制游戏，但其[启动脚本](https://github.com/BUTR/Bannerlord.GABS/blob/master/launch-bannerlord.ps1)仍运行BLSE /singleplayer及模块列表，未由此取得无界面原生战役能力；本轮未安装或运行它。Calradia.online页面抓取525，搜索摘要的完整headless宣称未核实，未采用。（依据：本机布局/原版枚举、官方与项目源文件核查 2026-10-19）
