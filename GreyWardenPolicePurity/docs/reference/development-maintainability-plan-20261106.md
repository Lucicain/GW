# 后续开发与可维护性方案

日期：2026-11-06。状态：建议稿，供本次路线决策；未实施工具退休、业务迁移或流程替换。
当前有效规则仍在 [workflow](../state/workflow.md)、[诊断](../state/diagnostics.md) 与 [代码健康](../state/code-health.md)。本文中的“建议”不能作为已获批准的新规则。

## 建议选择

让测试桥退出常规开发流程，停止以无人值守游玩为主要验证路线。推荐下一批退休目前的通用桥接设施，按需保留有实际用途的局部检查能力。分层继续，但先完成城内办案队这个试点，再决定下一处；不同时推进全仓迁移。

保留并改善“用户正常游玩，agent 自己取证、定位和修复”的协作方式。人负责体验与发现不符合预期的表现；agent 负责判断、日志分析、原版调查、局部验证和收尾。不给用户分配概率分支清单，不要求用户重复撞同一故障。

“AI 测试”需要拆开看：自动检查真实生产规则仍有价值；AI 编一个假世界再证明它能运行，没有相同的证明力；自动启动真实游戏也只是一个工具，不能据此声称验证了玩法。测试桥本身运行真实游戏，不能把它与假引擎混称，但它当前的收益不足以支持继续扩建。

## 判断依据

本次源码基线为 `a4476ef`。实际进度与缺口归 [分层试点](../state/code-health.md#分层架构城内办案队试点中)、[测试桥](../state/build-and-deploy.md#自动化实机测试桥) 和 [清理待办](../state/workflow.md#清理台账)，这里只说明决策依据：

- 桥维护了通信、线程、队列、跨帧存读档、进程与超时管理。战役中重新读档还有已登记的原版清理步骤缺口；它本身也需要验证。
- 桥是独立开发模组，不进入玩家包，只有专用会话启用。没有证据证明它已造成玩家现有故障；推荐退休的理由是维护收益不足，而非已证明它破坏游戏。

## 开发方式：一件事从改动走到收尾

1. **先写清这次要改变的行为。** 在所属 state 使用现有位置说明触发条件、预期结果和未确定点；不为每个小改动另建方案文件。一个批次围绕一个机制及其必要关联改动，避免玩法调整、分层迁移和测试框架建设混在一起。
2. **先查归属和原版，再选改法。** CodeGraph 找入口和调用方，state 找现行规则；涉及事件时序、存读档或原生行为时查原版手册/源码。调用图没有边不能证明可以删除。
3. **在归属方修机制。** 同一概念一处决定、同一资源一处写入；新入口调用它，避免每个报错点再补一个特殊条件。跨事件操作列清开始、完成、取消、失效、重复回调与加载接续；只检查本次会遇到的路径。
4. **选与问题匹配的验证。** 编译和兼容检查兜住机械错误；局部规则检查回答确定性问题；真实日志、转储和必要的引擎现场回答集成问题。交付分别写清通过什么、没覆盖什么。
5. **部署同一份产物，让正常游玩提供现场。** 保持现有 live 哈希核对。agent 自己读日志；未经过的路径继续登记，不能因为玩家没反馈就删掉未解决的问题。
6. **收尾时减少维护面。** 删除替换掉的分支、过期辅助函数和临时诊断；同步所属 state。新旧两套不能以“以后再看”为由永久并存。

### 分层的完成标准

读游戏状态、计算决定、执行动作三个职责清楚即可，不要求每个职责都新建工程或接口。

- 输入只包含决定所需的数据；输出表达决定及必要理由。不要把整个游戏对象复制成另一套世界模型。
- 生产执行直接使用这一份规则；测试不能复制规则当作期望值。期望应来自已明确的业务规则或已查实故障。
- 钱、兵、案件、差事占用仍经现有归属方改变。执行时重新核对可能变化的必要条件，区分“打算补派”与“实际补派成功”。
- 在真实调用处核对读取时机、短路顺序和副作用。影子决定相同只能证明记录到的决定相同，不能证明采集没有副作用、动作成功或加载正确。
- 不为统一目录大批搬文件，不先建通用事件总线、依赖注入或状态机框架。一个试点如果为验证不断需要新增基础设施，应缩小范围或撤出试点；已经投入不是继续扩张的理由。

## 概率故障怎样处理

| 看到的现象 | agent 先回答的问题 | 合适的证据与验证 |
|---|---|---|
| 某个结果一直没出现 | 入口、候选和配置引用是否有效？还是确实没抽中？ | 静态查入口与配置，再看实际候选、权重和抽签记录 |
| 抽到某分支后行为错误 | 规则选错，还是执行失败？ | 记录一次实际输入和决定；给同一生产规则指定抽签值检查边界；动作结果单独核对 |
| 玩很久才重复扣款/占案/丢兵 | 谁在什么顺序重复写入或漏了清理？ | 同一对象关联前后事件，查唯一写入方及开始后失效、重复、取消、加载路径 |
| 原生崩溃、动画或战场表现异常 | 哪个真实对象/生命周期出错？ | 转储、原版 C#/C++ 和必要的实机现场；不以纯逻辑测试冒充引擎验证 |

以概率为 25% 的规则为例：可以直接检查阈值两侧以及恰好等于阈值时的生产选择逻辑，不用人玩到两种结果都自然出现。整数权重则检查累计区间的首尾、零权重和合法抽签范围。证明“这个分支计算正确”与证明“真实游戏能够走到这里”是两件事，分别报告。

建议仅为值得验证的生产规则允许这种确定性检查，并在实施时明确更新当前离线测试口径；本轮没有据此新增测试。迁移保持随机调用次数、位置和消费顺序；记录已有抽签值，不再抽一次。固定全局种子不能保证整个 Bannerlord 重演，局部输入重算也不叫整局回放。

### 诊断留下经过，避免铺设第二套系统

复用现有日志，只对当前问题增加能回答问题的字段：构建/配置身份、对象稳定 ID、事件顺序或游戏时间、操作前状态、候选/权重及实际抽签值、决定原因、操作后结果。随机无关的问题无需记录抽签；跨事件问题才保留必要的前序变化。

正常路径尽量只计数；异常写证据。只有确实需要前序事件时才做有上限的最近记录，不默认引入全局录像、每 tick 全量扫描或新的监控平台。所有取证采集仍在诊断条件编译内，不吞异常、不修状态、不重复调用有副作用的评分或随机方法。

如果第一次反馈只能确认现象，agent 明确缺哪段证据并补诊断，用户照常玩。不能承诺下次必抓到，也不能把“证据不足”转化为让用户重走几十个细分支。

### 修复结论分开报告

建议在现有缺陷/待实测位置区分：**现象已记录 → 根因已证实 → 修复已验证到某一层 → 真实相关路径经过 N 次、复发 M 次**。

根因可由现场加源码/转储闭合；不必强求 AI 重演整个游戏过程。能做旧失败、新通过的负对照就在对应层做，并注明它是规则级还是引擎级。真实引擎没有重现时保留这个缺口，不把局部测试升级为完整验证；根因仍不明则只补取证，不猜改业务。

经过次数必须是相关条件真正成立、相应操作实际被尝试的次数，不能用开游戏次数或空转小时替代。连续 10 次无复发不是罕见故障已消失的证明。建议将现行固定退休门槛改成按缺陷条件、已取得的证据与剩余风险决定；用户确认后的退休仍按确认范围办理。这需要同步修改 diagnostics 与 workflow，尚未实施。

## 建议实施顺序与验收

| 批次 | 具体工作 | 完成标志 |
|---|---|---|
| 1：收束测试设施 | 让桥退出必经流程；核对引用后退休通用桥工程、启动服务、专属场景与专用接入。按实际用途审查辅助代码，不连带删除生产分层和有效诊断。历史由仓库存档保留，不维护第二套闲置桥 | 主模组可独立构建；没有悬空引用/专属运行模块残留；用户配置和存档保持；流程文字一致。若某能力确有不可替代的已证实用途，列出具体用途再局部保留 |
| 2：完成现有试点 | 处理无样本回放假通过和玩家版诊断采集；逐条核对旧分支与纯规则、读取时机、执行结果；利用正常游玩产生的真实样本补证据，再决定切换或撤出 | 切换后只保留一份生产决定，执行仍走归属方；未观察到的路径明确保留缺口。若无法收敛则撤出试点，不长期留下双轨 |
| 3：处理一个高价值真实问题 | 从现有缺陷中选影响大且证据可推进的一项；先取证，再修归属方。已有谈判抽签可作为后续局部随机规则候选，不与当前试点同时扩大 | 有根因证据、必要负对照或明确验证缺口、复发观测；修复减少散落条件，不带入新的通用框架 |
| 4：按已有台账增量清理 | 清掉本批旧路径、过期诊断、重复规则和悬空引用；用现有卫生、影响和新鲜度检查 | 清理项实际销账，新发现项有归属；无需再建“清理平台” |

批次 1 涉及删改机制，实施时按项目流程独立审查；本建议稿未执行删除。live 清理要先核对精确目标、占用情况和配置引用，不能顺带删除测试存档或改动第三方模组。源码稳定后构建、部署并核对哈希，体验由用户正常游玩确认。

实施路线变更时，一次同步 `AGENTS.md`、workflow 的故障修复、build-and-deploy 的桥与测试边界、diagnostics 的哨兵退休、code-health 的试点目标；删除被替代的旧句，不叠加另一套相反规则。用户本轮要求的是评估与落地方案，不能据此声称已批准删除所有测试或所有诊断。

## 怎样判断复杂度真的下降

继续使用现有清理台账，不加新看板。每批收尾回答四个问题：同一规则是否仍有多处实现？是否留下长期双轨？已知故障还缺哪段证据？新工具解决了哪个实际问题、维护成本是否值得？

既有规则数量可提示文档膨胀，但不能靠删掉有效约束刷低数字；文件少、函数短、测试多都不能单独证明优雅。更有用的完成标准是：修改一条规则能找到唯一入口，收到一个故障能追到发生经过，修完能删除旧补丁和临时设施。

本方案保留人类对体验的判断，同时把能够确定性核实的工作交回开发过程。真实引擎和长局仍有验证盲区；目标是让每次故障留下更多有效证据、下一次改动更局部，而不是承诺不再出现 bug。
