## 存档运行态（2026-09-23 直接解压读取）

存档去掉头部元数据后是原始 deflate 流；解出的 52,587,503 字节里，行为数据以
“值记录在前、键记录在后”成对存放，字符串经字符串表编号。读出的订单：

| 键 | 值 |
|---|---|
| `GWPP_PlayerTroopOrderTroopId` | `gwheavyinfantry` |
| `…Count` | 80 |
| `…Price` | 10080 |
| `…Stage` | 1 = `Training` |
| `…FiledHour` / `…LastXpHour` | 2192419.96 / 2194244.97（已训练约 1825 小时 ≈ 76 天） |
| `…NextContactHour` | -1（从未进入交付） |
| `…CohortPartyId` | `gwp_cohort_70911` |
| `…LastStockSourcePartyId` | `gw_leader_2_party_1` |

结合截图（71 重步兵 + 5 灰袍弓箭手 + 4 外来兵 = 80），**订单卡死已确认**：

1. 完成判定只数随行队里健康的目标兵：71 < 80，永远停在 `Training`。
2. `TopUpCohort` 空位 = 80 − 随行队总人数 80 = 0，训练官的兵补不进来。
3. 5 名弓箭手与 4 名外来兵既不能升成重步兵（灰袍树是新兵→预备→重步/弓手/骑士三叉，
   弓手与重步同为末级兄弟分支），也不在重步兵下游，拆编重训不处理；外来兵还被
   `IsGreyWardenTroop` 排除。它们永久占位。
4. 因为订单不结束，新练兵单与派遣下单的门禁都被挡住，对应入口消失。

**弓手来自我们自己的代码**：`TrainForOrderIfDue` 给随行队里的预备兵加经验；随行队无领主，
`PolicePartyTroopUpgradeModel.HasSteeredPreference` 为假，模型对灰袍三条分支一律给权重 1，
原版升级器于是把一部分预备兵升成弓手（骑士需马，无领主队多半不满足）。

**外来兵的入口已确认存在**：`PoliceResourceManager` 的纯化（每 6 小时与战后两处）都要求
`LeaderHero.Clan` 为灰袍，无领主随行队两处都不进；原版战后获救俘虏可写入参战 NPC 队名册。
（调查时）随行队也没有任何配船路径；现为出生时向练兵官借船，见 temporary-parties.md。

**“练好了”的高概率来源**：账簿 `GetPlayerOrderSnapshots` 的 `ReadyCount` 数的是训练官
**主队**的目标兵，而交付数的是随行队。训练官主队只要有 ≥80 名重步兵，账簿就显示练齐，
实际却永远交不了。尚需玩家确认看到的是否是账簿。

## 源码已确认

1. `GreyWardenTroopRequestBehavior.cs` 的完成判定（593–617）清点随行队里订单目标兵种的健康人数。
   `GreyWardenTroopRequestBehavior.Cohort.cs` 的 `TopUpCohort`（208–224）却按队伍总人数判断空位。
   主文件684–691只训练能升级成目标的灰袍；错分支和外来兵不会自动变成目标兵。
   **因此，若订单为80名重步兵，截图的71目标兵+9其他兵可形成“未完成但满员不补”的阻塞。**
   订单的实际目标/数量仍未从存档运行态读取。
2. 订单升级偏好仅识别练兵长主队（主文件146–154）；
   `GreyWardenTrainingBehavior.cs` 231–235对无领主队跳过偏好设置；
   `PolicePartyTroopUpgradeModel.cs` 41–50在无偏好时给多个灰袍升级分支同等权重。
   无领主随行练兵队存在练向错误分支的代码缺口，不能据此断言截图五名弓手的实际来历。
3. `GetPlayerOrderSnapshots`（主文件208）仍从练兵长主队计算 `ReadyCount`，
   完成/交付却使用随行队。这是账簿展示与实际交付计数的容器不一致，
   不能将其等同于已证实的“练好了”弹屏原因。
4. 随行队按设计跟随练兵长（Cohort 118–124）；完成后由练兵长主队找玩家，
   交付对话要求 `Delivering`、正确英雄、足量目标兵（主文件1085–1096、1191–1215）。
   无领主随行队没有专用交兵对话；直接点它不等于触发交付入口。
5. 新练兵单要求没有现有订单（主文件331–339）。士兵派遣下单还要求没有在途练兵使者
   （`GwpWardenDispatchDialogue.cs` 228–235）；若没有任何可办事项，普通兵交谈入口也会隐藏（158–162）。
   因此订单卡住可以关联多个入口消失，但尚未读取此存档的实际门禁状态。
6. 使者送达后订单独立存在；使者死亡移除派遣记录，不自动取消已送达训练单
   （`GwpWardenDispatchBehavior.cs` 143–153、810–834）。本次死亡阶段未知。
7. 随行队创建时清空默认名册，初次拨兵只收灰袍；但无领主队不在灰袍资源纯化入口内。
   原版 `MapEvent.LootDefeatedPartyPrisoners` 与战利品模型允许参与战斗的NPC队伍接收
   获救俘虏，`MapEventParty` 把接收名册写进其 `MemberRoster`；此路径不要求队伍有领主。
   因此若随行队参战，**无需其他模组也可能获得外来兵**。本档是否参战尚未知。
8. 使者返程（`GwpWardenDispatchBehavior.cs` 913–931）和练兵长找玩家
   （`GreyWardenTroopRequestBehavior.cs` 1191–1215）没有跨海可达性检查；
   随行队与使者创建时也没有明确配船路径。原版在目标位置无法通行时可能把目的地留在自身位置。
   因此玩家在海上可令无船追随方停滞，这是**独立于混兵的机制风险**，
   未证明本次使者确因它饿死或交付因此失败。

上述训练主文件、Cohort及升级模型与r12提交 `3c05934` 比较，相关功能逻辑没有差异；
后续变动为异常留痕及销毁辅助方法，不是本次才引入这些缺口。
