## 规则分三级

同一条约束，能机械检查就不写成文字，写成文字的要在改动时被点名复核。（依据：用户裁定 2026-10-21）

| 级别 | 放在哪 | 谁保证它被遵守 |
|---|---|---|
| 机械约束 | `tools/Check-CodeHygiene.py`（`OWNERS`、兜底、重复函数体）、离线测试、构建预检 | 预提交钩子和测试，违反就拒绝 |
| 判断型规则 | 所属 state 的硬规则（带 `依据：`） | `tools/Check-ChangeImpact.py` 在改到它或它的调用方时点名，agent 逐条复核 |
| 背景与过程 | journal、git 历史 | 不约束开发；不得从中恢复规则（依据：流程） |

迁移是渐进的：一条判断型规则被违反过、或这次改动碰到了它且能写成固定判断，就顺手把它变成检查，
并把 state 里那句改成指向检查。不做一次性全量迁移。（依据：设计——老代码一次补齐全套检查会被告警淹没）

## 改动流程的细节

- **影响分析**：`python tools/Check-ChangeImpact.py`（默认对比 `HEAD`，`--base <提交>` 换基线，
  `--depth 2` 多追一层调用方，`--no-rules` 只列文件）。它从 diff 找到改动落在哪些符号上，沿 CodeGraph 的
  调用/引用边找依赖它们的代码，按 `覆盖源码` 映射到 state 并列出硬规则；改到共享概念归属方、删了文件会单独提醒。
  调用图不含 Harmony 绑定、反射和原生调用，没列出的子系统不等于不受影响。（依据：流程）
- **复核**：点名的每条规则，改后仍成立就过；违反了就改代码；规则本身该变（用户新裁定、调查推翻旧结论）就原地改那一句并更新依据。（依据：用户裁定 2026-10-21）
- **审查**：涉及共享概念、跨子系统或删改既有机制的改动，提交前让一个不带编写上下文的审查者只看 diff
  和影响报告（Claude Code 的 `/code-review`；其他 harness 开新会话做同样的事）。（依据：设计——不带上下文的审查者更容易发现编写者的盲区）
- **state 什么时候改**：规则、阈值、行为结论、待实测、已知缺陷变了才改。源码动了而结论没变，不碰文档。（依据：用户裁定 2026-10-21）
- **journal 什么时候写**：调查过程、被否决的方案、不显然的取舍。普通实现与验证结果写在提交信息里。（依据：用户裁定 2026-10-21）

## 故障修复：先钉死根因，再改

闪退往往不留存档，玩家也复现不了；没把握的修改会让问题更难查、项目更糟。所以修 bug 的顺序固定如下。（依据：用户裁定 2026-10-21）

- **先定位**：从现场证据（崩溃转储、Steam 退出码、在役诊断日志、玩家描述）出发，反编译/反汇编查实相关原版规则，再用不开游戏的离线测试复现：直接加载游戏和模组 DLL，执行生产方法。方法和证据强弱见 `docs/reference/investigation-methods.md`。（依据：用户裁定 2026-10-21）
- **根因没钉死，不改业务代码。** 复现不了时，能做的是在 `#if GWP_DIAGNOSTICS` 内加强取证，并在所属 state 写明缺哪一段证据、下次触发时会记下什么；不做「可能是这里」的猜测式修改。（依据：用户裁定 2026-10-21）
- **修复带负对照**：同一个离线测试里，旧代码复现故障，新代码通过，测试留作回归。只证明了方法级决策的，按 investigation-methods「离线测试与完整战役模拟的证据边界」如实报告边界，不说成实机已验证。（依据：用户裁定 2026-10-21）
- **取证由 agent 自己控制**：崩溃和体验问题都不要求玩家复现特定场景或 bug，玩家没法精确复现。agent 自己判断要回答什么问题，在诊断版里加能回答它的状态快照、前后边界和失败参数，让玩家正常游玩时自然产生证据，再自己读日志闭合；一轮日志不够就再加强，不把「请你再试一次某场景」当作取证手段。（依据：用户裁定 2026-10-21）
- agent 可以自己跑离线测试，不需要用户；实机验收仍只由用户做（见 AGENTS 硬约束）。

## 文档

- `docs/state/` 是唯一事实来源，结论变了就原地改写，不追加「后来又改成…」。同一行为只在所属 state 定义，
  其他页面链接过去。每份只写硬规则（带依据）、当前设计要点、待实测、已知缺陷。超过 250 行或混入多个职责时
  按职责拆分，不靠合并长行或删有效规则压到阈值以下。（依据：用户裁定 2026-10-08）
- 头部固定格式见 [README](README.md#每个-state-文件的固定开头)。
- 约束以后开发的句子句末标依据，写法和推翻权限见 [README](README.md#硬规则要标依据)；检查脚本按行判断，一条规则写在一行里。（依据：流程）
- `docs/journal/<YYYY-MM>.md` 只追加，记录当时为什么这么想，不代表那样想是对的。不得从 journal 恢复已不在 state 里的规则、阈值或实现；state 里找不到的规则默认不成立。（依据：流程）
- 用户对模组和流程的新裁定、新给的资源，当轮写进对应 state：裁定标 `用户裁定 YYYY-MM-DD`；仓库外素材写绝对路径和身份（如「过渡素材，之后替换」）。推翻旧裁定就原地改掉旧句子，不得只留在对话或 agent 私有记忆里。（依据：流程）
- agent 的权限、审批、工具设置是会话设置，不写进仓库。
- 发现了但没修的缺陷写成一行 `已知缺陷：…`，progress.md 自动汇总。新写的源码当轮写进某个 state 的 `覆盖源码`。
- 生成的东西（code-map、progress.md 的待实测与已知缺陷汇总）只由脚本重建，不手写。（依据：用户裁定 2026-10-07）
- **没有无主的东西。** 分支、工作树、stash，以及 `.codex_tmp/`、`build-check/` 里的每一项，要么属于一件还在进行的事、
  在 state 或 `docs/reference/local-scratch.md` 里写明，要么不存在。state 里的回退指向提交号，不指向临时文件。（依据：用户裁定 2026-10-07）

## 提交与发版

- **提交时机是一件事到了稳定点**，不是一轮结束。稳定点：用户实测确认可用；一个功能或修复做完（构建、测试通过，
  已部署 live 等用户实测）；马上要动有风险的改动，需要一个能退回去的点。
  仍在试方案、预计继续改或撤的部署属于中间步骤，构建通过不自动等于方案稳定。（依据：用户裁定 2026-10-08）
- **粒度**：不强求一个提交只做一件事，相关或同期的改动可以一起提交，提交信息写清包含什么。（依据：用户裁定 2026-10-21）
  但不要碎提交：09-27 一天 39 个提交，双刀动画流水线 50 分钟提交了 11 次，不少只改了 journal 几行。（依据：用户裁定 2026-09-27）
  未提交的改动不要跨好几天堆积：下一个接手的 agent 分不清哪些做完了。（依据：流程）
- **推送、打 tag、建 Release、出 ZIP、改 `_Module/README.md` / `README_EN.md`**：只在用户提出新版本时做。
  普通开发构建永远不出 ZIP。「上一版」是哪个提交，以 [build-and-deploy](build-and-deploy.md)「已发布版本与下一版的对比基线」为准，
  不要只看 tag 名。发版按 `.claude/rules/release-notes.md` 与 `docs/reference/release-checklist.md` 做。（依据：用户裁定）
- 仓库 `Lucicain/GW` 是公开的，但玩家只看 Release 页。云端历史不删、不改写已推送的提交；本地 `.git` 可以瘦身。（依据：用户裁定）
- 替换或移除已有功能前，先在 state 里记下回退路径（哪个提交、哪些文件）。（依据：流程）
- 未提交改动的回退统一是：相对 `HEAD` 按这件事的方法差异撤销，不整体覆盖多件事共用的文件。state 里不为每轮写「本轮回退基线」。（依据：流程 2026-10-21）

## 多 agent 协作

- 同一块耦合区域同一时间只有一个 agent 在写；其他 agent 只读、调研或审查。（依据：用户裁定 2026-10-21）
- 互不相干的区域可以并行，各自用 worktree，开工前按领域（子系统）划好分工，不按文件临时分。
  worktree 只隔离文件，不隔离设计决定：两个并行任务碰到同一个共享概念，就改成先后做。（依据：设计）
- 交接只经仓库（state、提交、待实测），不经对话或某个 harness 的记忆。

## 定期集中清理

每次发版前，或用户要求时，集中做一次：`Check-CodeHygiene` 全量结果、绕过归属方的写法、重复实现、死代码、
state 里引用已失效的文件和符号、超长的 state、`.codex_tmp/` 与 `build-check/` 的无主项、遗留分支和 stash。
平时每轮只处理 `Check-StateFreshness` 点名的项，不做额外的整洁仪式。（依据：用户裁定 2026-10-21）
集中清理哪个 agent 都可以做，但同一时间只有一个在做，它就是这次的专职；开发中的 agent 不为此停下来。
漏网的死代码、文档错位、缺审查留到清理时处理，不为此再加机械检查。（依据：用户裁定 2026-10-22）

跨 agent 的共识只经下面这份台账，不靠哪个 agent 的记忆或对话：

- **增量清理**：清理只看 `git diff <上次基线>..HEAD` 和清理待办，不每次通读全库；做完把基线改成清理提交、删掉处理完的待办。
- **顺手登记**：开发中发现却不在本轮处理的整洁问题（关掉机制留下的代码、错位的文档段落、缺的审查、可合并的重复实现），
  写一行进清理待办，写清在哪、为什么，不在对话里说说就算。
- **收尾可见**：`Check-StateFreshness` 每次报告距上次清理多少提交、几项待办，只提示，不拦提交。

## 接入 harness

- AGENTS.md 是唯一入口。仓库目录里（本仓库及其上级目录）不要新建 `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md` 或 `GEMINI.md`。（依据：用户裁定 2026-10-07）
  前三个会让 Claude Code 不再读 AGENTS.md，`GEMINI.md` 在 Antigravity 里优先于它。用户主目录的 `~/.claude/CLAUDE.md` 不在此列，它放跨项目的个人习惯。
- harness 自带的记忆、规则、技能只放个人习惯或指回仓库的指针。Codex 的全局记忆对本项目关闭（`.codex/config.toml`）；
  Claude Code 项目记忆里的 project/feedback 条目要写 `仓库位置：<相对路径>`，检查脚本会点名没写的。（依据：用户裁定 2026-10-07）
- 新 harness 接进来时确认三件事：它读 AGENTS.md；它能跑 `tools/` 下的 Python 和 git 钩子；它自己的记忆按上一条设好。
  各 harness 的便利功能（Claude Code 的 `/wrap`、`.claude/rules/`、code-map 刷新钩子、CodeGraph MCP）只是加速，不是规则来源。
- 新克隆后设一次 `git config core.hooksPath .githooks`。
- CodeGraph：`codegraph status --json` 看索引与工作树差异，有变化时 `codegraph sync`；索引包含未提交源码，
  不是已发布版本的证明；本地数据库不入 git。MCP 查询失败用 CLI，CLI 也失败就用 code-map 与 `rg`，不把工具故障当成业务结论。（依据：流程）
